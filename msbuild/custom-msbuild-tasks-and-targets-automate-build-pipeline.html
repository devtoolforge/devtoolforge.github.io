Custom MSBuild Tasks and Targets: Automate Your Build Pipeline

Most teams treat their build as an untouchable sequence configured long ago, then compensate with fragile CI shell scripts. MSBuild offers a better path: custom targets and tasks that live in the repository, run identically on every machine, and hook directly into the build pipeline where they belong.

MSBuild

Most teams treat their build as an untouchable sequence configured long ago, then compensate with fragile CI shell scripts. MSBuild offers a better path: custom targets and tasks that live in the repository, run identically on every machine, and hook directly into the build pipeline where they belong.

This hands-on guide shows how to add custom targets with BeforeTargets and AfterTargets, write typed custom tasks in C#, package reusable build logic into a NuGet-integrated .props/.targets bundle, and debug the whole thing with binary logs. Your CI YAML shrinks, your local builds get smarter, and build knowledge stops living in one DevOps engineer's head.

Targets: Declarative Build Steps

A target is a named unit of build logic. Hooking into the pipeline needs no pipeline edits: declare BeforeTargets or AfterTargets against a built-in target and your step runs at the right moment on every machine that builds the repo.

<Target Name="VerifyApiCompat" AfterTargets="Build"
        Condition="'$(Configuration)' == 'Release'">
  <Message Importance="high" Text="Running API compatibility check..." />
  <Exec Command="dotnet apicompat -l "$(TargetPath)"" />
</Target>

The Exec task shells out to tools; Message writes to build output; Condition gates by configuration or property. Keep targets small, named after their intent, and stored in Directory.Build.targets at the repo root so every project inherits them.

Custom Tasks: Typed Build Logic

When Exec and inline property functions are not enough, write a task: a public class deriving from Microsoft.Build.Utilities.Task with typed properties as parameters and Execute() as the body. MSBuild instantiates it, injects values, logs through the provided Log helper, and treats a false return as build failure.

public class StampVersion : Microsoft.Build.Utilities.Task
{
    public string VersionFile { get; set; } = "";
    [Output] public string Stamp { get; private set; } = "";

    public override bool Execute()
    {
        Stamp = DateTime.UtcNow.ToString("yyyyMMdd.HHmm");
        File.WriteAllText(VersionFile, Stamp);
        Log.LogMessage("Stamped {0}", Stamp);
        return true;
    }
}

Register with UsingTask and call it from a target; Output parameters feed back into properties for downstream targets. Because tasks are compiled code, you get tests, debugging, and type safety that shell scripts never had.

Packaging Build Logic for the Organization

Shared build logic belongs in a NuGet package: put YourCompany.Build.props and YourCompany.Build.targets inside a build/ folder, pack it, and consume it via PackageReference. MSBuild imports those files automatically for every consumer, so central rules (versioning, warnings-as-errors, signing, SBOM generation) update everywhere with one package version bump.

Order matters for composition: props files run early in evaluation, targets run at execution; consumers can override anything via standard property precedence. Document the extension points the package offers, and treat its releases like any library: semantic versioning and a changelog.

Debugging Custom Build Logic

The binary log is the superpower: msbuild -bl writes every evaluation and task invocation to a structured file, and the free MSBuild Structured Log Viewer makes it searchable, showing exactly which target ran, with which property values, in which order. For evaluation questions, msbuild /pp:flatten.xml outputs the fully imported project.

dotnet msbuild -bl:build.binlog
# open build.binlog in MSBuild Structured Log Viewer
# or flatten all imports:
dotnet msbuild /pp:flatten.xml

Set MSBUILDDEBUGPATH and environment toggles when hunting engine-level issues, and add Message Importance=high lines temporarily, but prefer the log viewer; it answers where-did-this-value-come-from questions in seconds.

What Belongs in the Build, Not in CI YAML

Move anything that must be true of every build into targets: version stamping, API compatibility checks, code style enforcement, packaging metadata, artifact copying. Keep CI YAML for orchestration only: checkout, restore, build, test, publish. The division of labor keeps local builds honest (developers see the same steps) and makes CI files short enough to read.

Start small this week: add one AfterTargets=Build target that stamps a build time into output, and one Directory.Build.props with shared analysis settings. From there, every script you were maintaining in CI becomes a candidate for a home in the repo.

Conclusion

Custom MSBuild targets and tasks turn your repository into the single source of build truth. Hook targets into the pipeline, write typed tasks where logic deserves tests, distribute shared rules as a build package, and debug with binary logs. Your CI gets shorter, your team's builds get identical, and build knowledge finally lives in version control.

Frequently Asked Questions

Where should custom targets live?

In Directory.Build.targets at the repo root for repository-wide logic, or inside a NuGet package's build/ folder for organization-wide reuse. Project-level csproj edits are fine for single-project concerns.

Exec vs custom task: which should I use?

Exec is right for simple one-line tool invocations. Write a custom task when logic needs parameters typed, test coverage, or richer logging, or when the same shell command appears in multiple places.

How do I pass values between targets?

Output parameters from tasks (marked [Output]) write to properties or items, which downstream targets read. Declare the property in the task call and reference it later like any property.

Can I make a target run only in Release?

Yes: Condition="'$(Configuration)' == 'Release'" on the Target element gates execution, evaluated at execution phase per build.

How do I find out which target did something?

Capture msbuild -bl and open the log in the Structured Log Viewer; it lists every target and task with timing and inputs, searchable by name and property.
