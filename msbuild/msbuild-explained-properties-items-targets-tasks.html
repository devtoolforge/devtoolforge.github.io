This article is the mental model you wish you had on day one: how evaluation differs from execution, why properties and items behave differently, how targets chain through BeforeTargets and AfterTargets, and how to write custom tasks. Debugging build scripts stops being archaeology once this model clicks.

The Two Phases: Evaluation and Execution

MSBuild processes a project in two distinct phases. During evaluation, it reads the XML top to bottom, imports props and targets, and computes the final tables of properties (name-value pairs) and items (typed lists). During execution, it runs targets, which call tasks, using those tables as inputs.

Almost all MSBuild confusion comes from mixing the phases mentally. A property set inside a target does not affect evaluation-time logic that already ran; an item list defined after a target is still fully available at execution time. Once you ask which phase a line belongs to, build file behavior stops being mysterious.

Properties: Build Configuration Values

Properties are key-value strings that configure the build: TargetFramework, Configuration, OutputPath, Version. Set them in the project file, pass them on the command line with /p:, or import them from Directory.Build.props, which MSBuild automatically applies to every project in a folder tree.

<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <Nullable>enable</Nullable>
  <LangVersion>latest</LangVersion>
</PropertyGroup>

<!-- Directory.Build.props applies to the whole repo -->
<PropertyGroup>
  <Company>Acme Corp</Company>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>

Order matters during evaluation: later definitions override earlier ones, and command-line /p: values override everything. Conditional expressions ($(Configuration)=='Release') let properties adapt, but remember the condition is evaluated where the property is declared, in evaluation phase.

Items: Typed Lists of Inputs

Items are lists of things the build works on: Compile (source files), Reference (assemblies), PackageReference, Content. Unlike properties, items are collections with metadata, and they accumulate: Include adds, Remove subtracts, Update modifies metadata.

<ItemGroup>
  <Compile Include="**/*.cs" Exclude="bin/**;obj/**" />
  <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
</ItemGroup>

SDK-style projects define most items implicitly via wildcard globs, which is why modern csproj files are so short. You usually interact with items only to add a package, exclude a file, or copy content to the output, but the full item machinery is available when a custom build step needs inputs.

Targets and Tasks: The Execution Plan

A task is a single unit of build work, an atomic action: compile code, copy a file, run a tool. A target is a named group of tasks that runs as a unit, with declarative dependencies through DependsOnTargets, Inputs, and Outputs for incremental skipping. dotnet build is essentially msbuild /t:Build.

<Target Name="StampBuild" BeforeTargets="Build">
  <PropertyGroup>
    <BuildStamp>$([System.DateTime]::Now.ToString(yyyyMMddHHmmss))</BuildStamp>
  </PropertyGroup>
  <WriteLinesToFile File="$(OutputPath)stamp.txt"
                    Lines="Built at $(BuildStamp)" Overwrite="true" />
</Target>

Hook into the pipeline with BeforeTargets and AfterTargets rather than editing imported targets; the built-in Build, CoreCompile, and Publish targets are your extension points. The property functions syntax ($([System.DateTime]::...)) provides surprisingly deep inline logic without custom code.

Custom Tasks and Debugging

When inline logic is not enough, write a custom task: a public class implementing ITask (or deriving from Microsoft.Build.Utilities.Task) in an assembly referenced with UsingTask. The task receives typed parameters, does its work, returns true or false, and logs through the engine for build output.

Debugging builds has modern conveniences: msbuild -bl produces a binary log that the MSBuild Structured Log Viewer renders as a searchable timeline of evaluations, property values, and task inputs. For quick questions, msbuild /pp:out.xml flattens all imports into one file showing exactly what the engine sees, which instantly explains where a mystery property came from.

Conclusion

MSBuild is not magic; it is a two-phase XML programming language with four nouns. Learn properties and items as the data model, targets as the schedule, and tasks as the work, and every csproj in your organization becomes readable. Start with Directory.Build.props, add one BeforeTargets customization, open a binary log the next time a build surprises you, and the last mystery of the build file disappears.

Frequently Asked Questions

What is the difference between a property and an item in MSBuild?

Properties are single name-value strings used for configuration; items are typed collections (like Compile or PackageReference) with per-entry metadata that accumulate through Include/Remove/Update during evaluation.

How does dotnet build relate to MSBuild?

dotnet build is a thin wrapper that invokes MSBuild with the .NET SDK's logic loaded. Anything MSBuild can do, including /t: targets and /p: properties, is available through dotnet msbuild.

Where should shared build settings go?

Directory.Build.props (evaluation-time properties) and Directory.Build.targets (execution-time customization) in a repo root apply automatically to every project beneath that folder.

How do I see why a property has its value?

Run msbuild /pp:preprocessed.xml to flatten all imports, or capture msbuild -bl and open the binary log in the MSBuild Structured Log Viewer to see every property's origin and final value.

Can I write my own MSBuild task?

Yes. Implement Microsoft.Build.Framework.ITask in a .NET assembly, reference it with a UsingTask element, and call it from any target. Parameters map to task properties, and logging flows to the build output.
