What Is Property functions?

Property functions, in one sentence: $([System.DateTime]::...) and MSBuild function calls. In practice that means the details are worth getting right once, because everything downstream inherits the decision. The key is treating it as a living part of the workflow rather than a one-time setup task.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around property functions comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Best Practices for Property functions

These are the practices we see on teams where this area simply never causes drama:

  • Automate the boring parts of property functions with scripts or tasks; humans are bad at remembering commands.
  • Prefer small, reversible changes over big-bang migrations nobody can review.
  • Start every project with a documented property functions setup so the whole team follows the same conventions from day one.
  • Pin versions and record why each choice was made, so upgrades are decisions instead of accidents.
  • Measure before and after changes to property functions so decisions are driven by data rather than vibes.

None of these are hard individually. The discipline is doing them every time, which is why automation and CI checks carry so much of the load.

Performance Considerations

Watch the tails, not the averages. Median numbers hide the p95 and p99 latencies that users actually feel. For property functions workloads, repeated runs under realistic data sizes reveal the variance that a single clean run misses. Set a budget for the worst case, not the best case, and design for it.

Remove work before making work faster. The cheapest optimization for property functions is usually doing less: fewer allocations, fewer passes, fewer round trips. Profile to find work that can be skipped entirely under normal conditions. Only then reach for caching, and only with an explicit invalidation plan.

Tooling and Ecosystem

The surrounding ecosystem matters as much as the core feature. Around MSBuild, the tools that pay off fastest are the Structured Log Viewer, dotnet msbuild, Directory.Build.props, MSBuild Structured Logs. Each one removes a specific kind of manual work, and together they cover the whole loop from writing to verification.

Troubleshooting Property functions

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • It fails only in CI but passes locally — compare build modes and clean versus incremental state; CI reveals stale-output bugs instantly
  • It worked yesterday and nothing was changed — check what the OS, SDK, or package manager updated overnight before blaming the code
  • Errors mention a file or component you never touched — trace the first error in the log, not the last one — the real cause is almost always earlier

If none of these match, capture a full log before changing anything. For property functions that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

Is Property functions still relevant in 2026?
