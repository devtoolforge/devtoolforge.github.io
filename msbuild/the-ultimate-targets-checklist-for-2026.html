What Is Targets?

Targets, in one sentence: named units of work that run tasks in order. In practice that means the details are worth getting right once, because everything downstream inherits the decision. Once the defaults are deliberate, the rest of the workflow tends to fall into place.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around targets comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Why Bother with Targets?

"Why bother" is a fair question for any tooling topic. Targets earns its keep in three concrete ways:

  • It lowers maintenance cost because every future change starts from a sane baseline.
  • It reduces build and integration surprises, the kind that derail an otherwise calm sprint.
  • It cuts repetitive work out of the daily loop, which is where most of the hidden cost of tooling lives.

Notice what is missing from that list: fashion. None of these benefits expire with a release cycle, which is why targets keeps showing up in every serious MSBuild conversation. It is one of the few practices that pays for itself within the first week of consistent use.

Notice how much of the value comes from the boring parts: writing things down, pinning versions, automating checks. That is not an accident — targets rewards exactly the habits that compound everywhere else in MSBuild.

Troubleshooting Targets

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • It worked yesterday and nothing was changed — check what the OS, SDK, or package manager updated overnight before blaming the code
  • It fails only in CI but passes locally — compare build modes and clean versus incremental state; CI reveals stale-output bugs instantly
  • It fails intermittently under load — look for shared state and timing assumptions that only break when things overlap

If none of these match, capture a full log before changing anything. For targets that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

Quick Example

Here is a compact, real-world xml example you can adapt directly. It shows the configuration style we recommend for targets: explicit, commented where it matters, and free of magic.

<ItemGroup>
  <Compile Include="**/*.cs" Exclude="bin/**;obj/**" />
  <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
</ItemGroup>

Copy it, run it once, then trim it to what your project actually needs. The worst version of any snippet is the one nobody on the team fully understands.

A Practical Workflow

A repeatable workflow turns targets from a personality trait into a team capability:

  1. Automate the step so it runs without anyone remembering the manual command.
  2. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.
  3. Audit the current state: list what targets touches in your project today.
  4. Review the setup with the team and record one owner responsible for it.
  5. Document the rollback path before you need it, not during an incident.

This loop — audit, change, automate, verify — is deliberately generic. It fits MSBuild at any scale and survives every tooling generation we have seen.

Step-by-Step Quickstart

Can Targets be automated?

Yes, and it should be. Start by scripting the steps in this guide, then wire them into CI so the automation runs without anyone remembering to.

Do I need Targets for small projects?

More than you would expect. Small projects benefit disproportionately because there is no dedicated ops person to catch drift — the setup protects itself.
