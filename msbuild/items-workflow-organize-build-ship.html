What Is Items?

Items, in one sentence: typed input lists (Compile, Reference, Content) with metadata. In practice that means the details are worth getting right once, because everything downstream inherits the decision. Teams that invest here early spend measurably less time firefighting later in the project.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around items comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

The Mechanics of Items

Declare ItemGroups with Include/Exclude/Update. That is the core of it, and the steps below turn the idea into muscle memory:

  1. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.
  2. Document the rollback path before you need it, not during an incident.
  3. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.
  4. Review the setup with the team and record one owner responsible for it.
  5. Write the chosen setup down in the repository so the decision survives the next refactor.

Notice how much of the value comes from the boring parts: writing things down, pinning versions, automating checks. That is not an accident — items rewards exactly the habits that compound everywhere else in MSBuild.

Common Items Mistakes

The same failure patterns show up again and again. Here are the four we meet most often, including the classic: Fighting SDK implicit globs by re-adding files that are already included.

  • Optimizing before measuring, then optimizing again after the metrics disagree.
  • Skipping documentation for decisions, forcing archaeology six months later.
  • Copying configuration from an old project without understanding what it does today.
  • Assuming the default configuration matches your project's real requirements.

Every one of these fixes is cheap when caught early and expensive when caught late. A quarterly review of items — twenty minutes, honestly — catches most of them before they metastasize.

Troubleshooting Items

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • It works on one machine and fails on another — diff the versions and configuration first — environment drift explains most of these bugs
  • It fails intermittently under load — look for shared state and timing assumptions that only break when things overlap
  • It fails only in CI but passes locally — compare build modes and clean versus incremental state; CI reveals stale-output bugs instantly

If none of these match, capture a full log before changing anything. For items that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

Advanced Tips

Once the fundamentals are second nature, these are the practices that separate good setups from great ones:

  • Wrap external flakiness with retries and clear timeouts so failures are visible instead of mysterious.
  • Record decisions next to the code they affect, in the same pull request that introduces them.
  • Version your conventions: what worked for a two-person team needs revision at ten, and that is normal.
  • Tip: Inspect final items with the /pp preprocessed output or a binary log

Step-by-Step Quickstart

For readers who want the shortest possible path, here is the compressed version:

  1. Add a check to CI so regressions in items fail loudly instead of silently.
  2. Schedule a short review each quarter to prune what no longer earns its place.
  3. Review the setup with the team and record one owner responsible for it.
  4. Audit the current state: list what items touches in your project today.
  5. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.
  6. Add a check to CI so regressions in items fail loudly instead of silently.

Each step stands alone, so partial adoption already helps. Do them in order and the later ones get easier.

Frequently Asked Questions

What are the most common mistakes with Items?

The big three: treating it as a one-time setup, letting local configuration drift from CI, and skipping documentation for the decisions you make. All three are covered above with concrete fixes.

How long does it take to get comfortable with Items?

The basics take an afternoon; reliable habits take a few weeks of real use. The guide's checklist is designed to compress that ramp-up by focusing on what actually matters.

Can Items be automated?

Yes, and it should be. Start by scripting the steps in this guide, then wire them into CI so the automation runs without anyone remembering to.

Do I need Items for small projects?

More than you would expect. Small projects benefit disproportionately because there is no dedicated ops person to catch drift — the setup protects itself.

Conclusion

Treat this guide as a starting inventory, not a finish line. Re-run the checklist whenever your team, toolchain, or scale changes, and Items will stay an asset instead of becoming archaeology.
