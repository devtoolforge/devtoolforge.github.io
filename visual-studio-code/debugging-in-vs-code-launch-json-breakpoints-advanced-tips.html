Debugging in VS Code: launch.json, Breakpoints, and Advanced Tips

VS Code's debugger is one of its best features and one of its least explored. Beyond F5 lies a configuration system (launch.json) that reproduces any runtime environment, breakpoint types that watch data instead of lines, and techniques — logpoints, conditional hits, compound debugging, remote containers — that turn debugging from print-statement archaeology into a precise instrument.

launch.json Without the Guesswork

Press F5 with no config and VS Code offers to generate one for your detected runtime. The generated file is a starting point: what matters is the type (debugger), request (launch vs attach), program (entry point), and env/args that reproduce your real environment.

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": ".NET: Launch API",
      "type": "coreclr",
      "request": "launch",
      "program": "${workspaceFolder}/src/Api/bin/Debug/net10.0/Api.dll",
      "env": { "ASPNETCORE_ENVIRONMENT": "Development" },
      "cwd": "${workspaceFolder}/src/Api"
    }
  ]
}

Commit launch.json (and tasks.json it references) to the repository: everyone on the team gets identical debugging with one F5. Use ${workspaceFolder} and ${env:} variables instead of absolute paths so configs stay portable.

The Breakpoint Toolbox

Line breakpoints are the beginning. Right-click any breakpoint to add a condition (expression that must be true) or a hit count (break on the Nth pass), which transforms loop debugging from stepping hundreds of times into one targeted pause. Logpoints print an expression to the debug console without pausing at all — the print-debugging you love, without editing code.

  • Conditional: order.Status == 'failed' — break only on the interesting case
  • Hit count: break on the 50th iteration, not the first
  • Logpoint: log cart.items.length without stopping execution
  • Function breakpoint: break when any code enters a named function (great for library code)
  • Data breakpoints (where supported): pause when a variable's value changes

Combine freely: a conditional logpoint on a function breakpoint is a precision instrument inside code you do not own.

Inspecting Like a Pro

The Variables pane expands everything, but the Watch pane is where senior debugging happens: add live expressions (orders.Sum(o => o.Total) in C#, JSON.stringify(state) in JS) that re-evaluate on every pause. The Debug Console evaluates arbitrary expressions against the paused context, including method calls and object mutation when you need to test a fix before writing it.

Learn the hover-to-inspect and inline values settings (debug.inlineValues) to see state without opening panes. When call stacks get deep, the Call Stack pane's per-frame click lets you evaluate variables in any frame's scope, not just the leaf.

Multi-Process and Remote Debugging

Compounds configurations run several debug sessions in one F5: launch the API and the frontend dev server together, or a service and its worker. In launch.json, a compounds section references named configurations, and each keeps its own console and control.

Remote is where VS Code leaves classic IDEs behind: attach over SSH, debug inside WSL, attach to a running Docker container, or debug Chrome via the browser debugger — all first-party. The pattern is identical: install the remote extension, reopen the environment, and your launch.json works there unchanged.

Habits That Speed Up Every Session

  • Bind step-over/into/out and toggle breakpoint to comfortable keys; mouse-debugging is slow
  • Keep a scratch Watch list per project committed in .vscode for the variables you always check
  • Prefer logpoints for loop scans, conditional breakpoints for rare paths
  • Use the Debug Console to prototype the fix, then paste it into the editor
  • When a bug needs three or more breakpoints twice a week, codify it as a launch configuration

Conclusion

VS Code debugging rewards deliberate setup: a committed launch.json, the full breakpoint toolbox, live watch expressions, and compound or remote configurations for real architectures. Adopt even half of this and you will spend less time reproducing bugs and more time fixing them, in any language the extension marketplace supports.

Frequently Asked Questions

Where does launch.json go?

In the .vscode folder at the workspace root. Commit it so teammates get the same debugging experience; keep machine-specific values in ${env:} variables or a separate uncommitted config.

What is the difference between launch and attach?

Launch starts the program under the debugger; attach connects to an already-running process (a server, container, or remote host). Both use the same breakpoints and panes.

Can I debug two processes at once?

Yes. Define multiple configurations and list them under compounds in launch.json; one F5 starts them together with independent sessions.

How do logpoints work?

A logpoint is a breakpoint that logs an expression to the debug console and continues without pausing, so you get print-style output without modifying source code.

Can I debug code running in Docker or WSL?

Yes, first-party: the Dev Containers and WSL extensions attach debuggers inside those environments, and your launch.json configurations work there just as locally.
