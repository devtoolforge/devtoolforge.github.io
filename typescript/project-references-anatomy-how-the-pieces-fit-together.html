What Is Project references?

Project references, in one sentence: splitting builds into composable sub-projects. In practice that means the details are worth getting right once, because everything downstream inherits the decision. Teams that invest here early spend measurably less time firefighting later in the project.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around project references comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Project references vs Readonly and immutability

They overlap enough that the question is usually about trade-offs rather than right and wrong. Troubleshooting Project references

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • It works on one machine and fails on another — diff the versions and configuration first — environment drift explains most of these bugs
  • It fails intermittently under load — look for shared state and timing assumptions that only break when things overlap
  • Performance collapsed after an upgrade — bisect the upgrade by rolling back one component at a time and re-measuring

If none of these match, capture a full log before changing anything. For project references that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

A Practical Workflow

A repeatable workflow turns project references from a personality trait into a team capability:

  1. Document the rollback path before you need it, not during an incident.
  2. Review the setup with the team and record one owner responsible for it.
  3. Write the chosen setup down in the repository so the decision survives the next refactor.
  4. Automate the step so it runs without anyone remembering the manual command.
  5. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.

This loop — audit, change, automate, verify — is deliberately generic. It fits TypeScript at any scale and survives every tooling generation we have seen.
