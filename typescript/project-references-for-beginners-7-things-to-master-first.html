What Is Project references?

Project references, in one sentence: splitting builds into composable sub-projects. In practice that means the details are worth getting right once, because everything downstream inherits the decision. The key is treating it as a living part of the workflow rather than a one-time setup task.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around project references comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Why Bother with Project references?

"Why bother" is a fair question for any tooling topic. Project references earns its keep in three concrete ways:

  • It turns tribal knowledge into something a newcomer can read, run, and verify.
  • It makes onboarding dramatically easier: new developers find rails instead of folklore.
  • It reduces build and integration surprises, the kind that derail an otherwise calm sprint.

Notice what is missing from that list: fashion. None of these benefits expire with a release cycle, which is why project references keeps showing up in every serious TypeScript conversation. The key is treating it as a living part of the workflow rather than a one-time setup task.

Performance Considerations

Change one thing at a time. Stacked optimizations hide which change actually helped and which added complexity for nothing. Re-run the same measurement after each adjustment to project references and keep a short log of results. When two changes interact, test them separately before combining, or you will ship mystery performance.

Watch the tails, not the averages. Median numbers hide the p95 and p99 latencies that users actually feel. For project references workloads, repeated runs under realistic data sizes reveal the variance that a single clean run misses. Set a budget for the worst case, not the best case, and design for it.
