TypeScript is in the middle of the biggest platform shift in its history: TypeScript 6.0 is the final release built on the original JavaScript codebase, while TypeScript 7.0 completes the native Go port that Microsoft calls the most requested improvement in the project's history, promising roughly ten times faster compilation.

If you maintain a large TypeScript project, the next few months of tooling decisions matter more than any language feature in years.

The Two-Track Plan, Explained

Microsoft is steering TypeScript along two parallel tracks. TypeScript 6.0 continues the classic JavaScript compiler: it is the bridge release that deprecates behaviors and flags destined for removal and keeps the ecosystem stable. TypeScript 7.0 is the native port written in Go, revealed in March 2025 and developed in the open as typescript-go, with the tsgo command-line binary.

The distinction matters because 6.0 and 7.0 are designed to coexist for a while: many toolchains will run 6.0 for editor and API scenarios while using 7.0 (tsgo) for type checking and builds, which is safe because testing shows 7.0 finds essentially the same errors: across roughly 20,000 compiler test cases, all but a few dozen matched 5.9/6.0 behavior.

What TypeScript 6.0 Changes

6.0 is a cleanup release. Deprecations target flags and behaviors scheduled for removal in 7.0: legacy module-resolution corners, obsolete compiler options, and edge-case type inference quirks that modern code never touches. For a typical modern project with moduleResolution bundler or node16, the upgrade from 5.9 is routine.

Language-level additions in the 5.x line continue, but Microsoft has been explicit that 6.0 exists to make the jump to 7.0 boring. Run the deprecation report early: the issue tracker lists every upcoming removal so you can search your tsconfig and scripts for affected flags now.

TypeScript 7 (tsgo): What Improves

  • Compile and type-check speed in the ~10x range on large codebases
  • Shared-memory parallelism for language service operations
  • Lower memory use on monorepos
  • Feature parity for type checking, --incremental, project references, and --build mode
  • Native VS Code language service preview from the Marketplace

What is explicitly not there at launch: the old compiler API (Strada), full JavaScript emit parity for every corner, and some watcher behaviors. Teams that only build and type-check can adopt tsgo early; tools that consume the compiler API need time to port to the new API surface.

How Your Build Pipeline Is Affected

Most pipelines change with one word: swap tsc for tsgo in CI and watch builds land minutes faster on large repos. Keep tsconfig unchanged; the port honors the same files and module resolution. Bundler users (Vite, esbuild, swc) already delegate type checking separately, and tsgo slots into exactly that hole with a fraction of the cost.

Plan a canary phase: run both compilers in CI for a week, diff their outputs, then flip the default. Because type checking is the slow half of most builds, the speedup compounds with every pull request, which is where developer experience really pays off.

Preparation Checklist for Teams

  • Upgrade to 5.9/6.0 and fix all deprecation warnings now, while fixes are cheap
  • Inventory tooling that imports the typescript npm package (custom lint rules, codegen) and plan their move to the new API
  • Standardize tsconfig on modern moduleResolution to avoid legacy corners
  • Try tsgo on a side branch; record error diffs and build times for your repo
  • Keep an escape hatch: both compilers can coexist per-script until confidence is total

None of this requires a rewrite. The single biggest win for most teams is simply clearing deprecations early so the 7.0 migration day is a config edit instead of a project.

Conclusion

The 6.0-to-7.0 handoff is TypeScript's infrastructure decade in miniature: a stable bridge release, then a native engine that makes big projects feel small again. Upgrade to 6.0, clean your deprecated flags, and pilot tsgo in CI. By the time 7.0 is your default, your team will wonder how you ever waited on tsc.

Frequently Asked Questions

Will TypeScript 7 break my existing code?

No. The port preserves the same files, module resolution, and type-checking behavior, with testing showing near-complete error parity with 5.9/6.0. Only deprecated flags and behaviors removed in 6.0 disappear.

Should I switch to tsgo today?

For build and type-check scenarios, many teams already do, validating outputs against tsc during a canary period. Editor and API-dependent tooling should wait for or verify full parity on your codebase.

What happens to the TypeScript compiler API?

TypeScript 7 does not support the old (Strada) API. Tools that consume the compiler API will move to the new native API as it stabilizes; most end-user projects are unaffected.

Is TypeScript still open source?

Yes. Both the classic compiler and the typescript-go port are developed in the open on GitHub under the Apache 2.0 license.

Why Go and not Rust or C#?

Microsoft chose Go for its structural similarity to the existing codebase (garbage collection, data patterns), which enabled a mechanical port with parallelism gains, rather than a risky architectural rewrite.
