What Are the Build Tools?

The Visual Studio Build Tools package the same compilers and build engine that power Visual Studio, minus the IDE shell. You get MSBuild, the Roslyn C# and VB compilers, the F# compiler, the .NET SDK, the Visual C++ toolset, NuGet, and workload-selected components such as web targets, desktop SDKs, or Azure libraries.

Because everything is invoked from the command line, the Build Tools are the standard choice for CI/CD agents: Azure Pipelines, GitHub Actions self-hosted runners, Jenkins nodes, and Docker build containers. Your pipeline calls MSBuild or dotnet build exactly as it would on a developer machine.

Silent Installation with Exactly What You Need

The installer's --add flags select workloads and components, making installs fully scriptable. Identify the smallest workload set that builds your solution by checking each project's target and references, then codify it in your agent provisioning script.

vs_BuildTools.exe --quiet --wait --norestart ^
  --add Microsoft.VisualStudio.Workload.ManagedDesktopBuildTools ^
  --add Microsoft.VisualStudio.Workload.WebBuildTools ^
  --add Microsoft.VisualStudio.Workload.VCTools;includeRecommended ^
  --add Microsoft.Net.Component.4.8.1.SDK

Record the exact command in version control next to your agent image or Dockerfile. When a project adds a component (a new targeting pack, a newer Windows SDK), update the provisioning script, not the agent by hand, so every agent stays reproducible.

Sizing and Maintaining CI Agents

Start from the base OS image, install the Build Tools with your workload list, cache the NuGet global packages folder, and snapshot the result (VM image, container layer, or cloud agent template). Expect 2-8 GB for .NET-only agents and considerably more when the C++ toolset or Android/iOS workloads are included.

Two maintenance rules prevent classic build-agent rot. First, pin SDK versions with a global.json so agents use the SDK your repo expects, and update that pin deliberately. Second, periodically rebuild agents from the provisioning script rather than patching them in place; drift between agents is the leading cause of builds that pass on one machine and fail on another.

Licensing: Build Servers vs Developer Seats

Build machines require their own licensing treatment. Visual Studio Professional and Enterprise include build server licenses, and for some products the Build Tools themselves are freely installable on build agents; but the rules differ per component and per edition, so verify the current Visual Studio licensing white paper for your mix.

In practice: count build agents as part of your Visual Studio licensing footprint, do not assume your developer Community edition covers the CI server, and document the license basis for each agent in your infrastructure repository. Audits always start there.

Build Tools in Containers

For isolated, disposable builds, Microsoft publishes Docker images with the Build Tools preinstalled, and you can bake your own from the installer script inside a mcr.microsoft.com/windows/servercore or server base image. A typical .NET pipeline builds in a container, publishes artifacts to a volume, and discards the container, guaranteeing clean environments per run.

FROM mcr.microsoft.com/dotnet/sdk:10.0
WORKDIR /src
COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /out

Containers also sidestep version drift entirely: the image tag is the environment. For C++ projects, container images with the VC++ toolset remove the last excuse for works-on-my-agent failures.

Conclusion

The Visual Studio Build Tools are the professional way to provision build capacity: scriptable, lean, and identical to what your developers compile with. Define your workload list once, bake it into images or containers, license agents correctly, and your CI pipeline becomes boring, in the best possible way.

Frequently Asked Questions

Do I need a Visual Studio license to use the Build Tools?

Developer seats follow normal Visual Studio licensing. Build servers and agents have their own licensing rules defined in the Visual Studio licensing white paper; Professional and Enterprise subscriptions include build server rights, and verify current terms for your edition mix.

Can the Build Tools compile C++?

Yes. Adding the VCTools workload installs the full MSVC compiler toolset, Windows SDK, and related components, enabling C++ builds from MSBuild or the command line without the IDE.

How is this different from installing the .NET SDK?

The .NET SDK alone builds modern .NET apps. The Build Tools add MSBuild with Visual Studio targets, .NET Framework targeting packs, the C++ toolset, and other components that full-framework and mixed solutions require.

Can I install Build Tools on a Docker container?

Yes. Microsoft documents Dockerfile patterns for installing the Build Tools in Windows container images, and publishes prebuilt images for common scenarios.

How do I keep agents at a specific SDK version?

Pin with a global.json file in the repository specifying the SDK version. Agents with multiple SDKs installed will honor the pin, and you update it deliberately per repository.
