Understand Deferred Execution First

Most LINQ operators do not run when written; they build a pipeline that executes on enumeration. That enables composition and avoids premature work, but it surprises developers twice: a query re-runs every time it is enumerated, and it sees the data as it is at enumeration time, not definition time.

var expensive = orders.Where(o => o.Total > 1000);  // nothing runs yet
// ... collection mutated ...
foreach (var o in expensive) { }   // runs here, over current data
var snapshot = expensive.ToList(); // materialize once, reuse safely

Rule of thumb: compose freely, then materialize exactly once (ToList, ToArray, ToDictionary) before reuse. If a method receives IEnumerable and enumerates it more than once, accept IReadOnlyCollection instead or snapshot inside.

Readability: Chain, Name, Project

Method syntax chains read top-to-bottom like a dataflow description; keep them that way by putting one operation per line, ordering from the most selective filter to projections, and extracting non-obvious lambdas into well-named local functions. Query syntax shines for joins and groupings; mixing both is idiomatic.

var risky = customers
    .Where(c => c.CreditScore < 600)
    .Select(c => new RiskRow(c.Id, c.Name, c.Balance))
    .OrderByDescending(r => r.Balance)
    .Take(50)
    .ToList();

Project early with Select into a narrow record instead of dragging entire entities through the pipeline: less memory, less accidental mutation, and an obvious shape for consumers.

EF Core: Keep Queries Translatable

EF Core translates LINQ to SQL, so anything the provider cannot translate either throws or silently evaluates client-side (older versions) — both bugs. Keep server queries to translatable operators, use AsNoTracking() for read-only queries, and let Select project only needed columns instead of fetching whole entities.

Performance Traps That Matter

  • Multiple enumeration: the classic silent 10x cost; materialize once
  • Count() when Any() suffices: Any stops at the first match
  • Concatenating lists in loops: use Collect or SelectMany instead
  • OrderBy on unbounded data in memory: consider a priority structure for huge sets
  • Parallel LINQ (AsParallel) by default: measure; PLINQ pays only for CPU-bound work on large inputs
  • Ignoring allocation in hot paths: closures capture variables; hoist constants out of lambdas

None of this argues against LINQ; the JIT optimizes simple pipelines well. It argues for measuring: a benchmark or a profiler row tells you which of these rules actually bites your workload.

Patterns Worth Adopting

Adopt three small patterns for durable data code. First, repository methods return IQueryable only internally and expose materialized IReadOnlyList results, keeping deferred execution from leaking across layers. Second, name projections as records (RiskRow above) so consumers get intent plus immutability. Third, centralize repeated predicates as Expression> constants so EF Core reuses translations across queries.

With those in place, code review of LINQ becomes checklist-fast: single materialization, translatable operators, early projection, explicit ordering before paging. Boring, readable, fast — exactly what production data code should be.

Conclusion

LINQ mastery is less about exotic operators and more about execution discipline: know when queries run, materialize deliberately, project early, and keep EF queries translatable. Internalize the handful of rules above and the same declarative style that makes LINQ pleasant to write will make it fast to run and easy to review.

Frequently Asked Questions

When does a LINQ query actually execute?

Deferred operators (Where, Select, OrderBy) run when enumerated, not when defined. Immediate operators (ToList, Count, First, ToDictionary) execute right away by enumerating the pipeline.

Why is multiple enumeration a problem?

Each enumeration re-runs the whole pipeline, re-fetching data and re-computing filters. Materialize once with ToList or ToArray when you plan to use the results more than once.

Should I always use AsNoTracking in EF Core?

For read-only queries, yes: it skips change-tracking overhead and is typically faster with less memory. Only tracked queries should be used when you intend to save changes to the fetched entities.

Is query syntax or method syntax better?

They compile to the same calls. Method syntax covers everything and chains cleanly; query syntax reads better for joins and grouping. Most codebases mix them by situation.

When is AsParallel worth it?

For CPU-bound transformations over large in-memory collections. It adds overhead and ordering caveats, so measure first; it rarely helps I/O-bound or small workloads.
