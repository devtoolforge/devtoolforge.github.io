What Is Global.json?

Global.json, in one sentence: the file that pins the SDK version for a repository. In practice that means the details are worth getting right once, because everything downstream inherits the decision. Small teams benefit as much as large ones, often faster because they can change habits quickly.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around global.json comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Tooling and Ecosystem

The surrounding ecosystem matters as much as the core feature. Around .NET, the tools that pay off fastest are the dotnet CLI, NuGet, EF Core, xUnit. Each one removes a specific kind of manual work, and together they cover the whole loop from writing to verification.

Global.json vs Single-file publish

They overlap enough that the question is usually about trade-offs rather than right and wrong. Global.json optimizes for ci and teammates build with exactly the sdk the project expects; Single-file publish pushes harder on the opposite axis. List your constraints honestly — team experience, platform targets, and maintenance budget — and the answer usually picks itself.

Start from the problem, not the tool. If your pain is ci and teammates build with exactly the sdk the project expects, Global.json is the more direct route; if your team already lives in the other ecosystem, Single-file publish minimizes ramp-up cost. Whatever you choose, write down why, because the next person will ask.

Troubleshooting Global.json

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • Performance collapsed after an upgrade — bisect the upgrade by rolling back one component at a time and re-measuring
  • It worked yesterday and nothing was changed — check what the OS, SDK, or package manager updated overnight before blaming the code
  • It fails only in CI but passes locally — compare build modes and clean versus incremental state; CI reveals stale-output bugs instantly

If none of these match, capture a full log before changing anything. For global.json that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

Quick Example

Here is a compact, real-world dockerfile example you can adapt directly. It shows the configuration style we recommend for global.json: explicit, commented where it matters, and free of magic.

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "Api.dll"]

Copy it, run it once, then trim it to what your project actually needs. The worst version of any snippet is the one nobody on the team fully understands.

  1. Add a check to CI so regressions in global.json fail loudly instead of silently.
  2. Automate the step so it runs without anyone remembering the manual command.
