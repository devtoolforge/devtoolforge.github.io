What Is Global.json?

Global.json, in one sentence: the file that pins the SDK version for a repository. In practice that means the details are worth getting right once, because everything downstream inherits the decision. It is one of the few practices that pays for itself within the first week of consistent use.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around global.json comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

The Mechanics of Global.json

Run dotnet new globaljson --sdk-version and commit it to the repo root. That is the core of it, and the steps below turn the idea into muscle memory:

  1. Add a check to CI so regressions in global.json fail loudly instead of silently.
  2. Pick the smallest meaningful change you can ship and measure — momentum matters more than scope.
  3. Write the chosen setup down in the repository so the decision survives the next refactor.
  4. Document the rollback path before you need it, not during an incident.
  5. Automate the step so it runs without anyone remembering the manual command.

Notice how much of the value comes from the boring parts: writing things down, pinning versions, automating checks. That is not an accident — global.json rewards exactly the habits that compound everywhere else in .NET.

Best Practices for Global.json

These are the practices we see on teams where this area simply never causes drama:

  • Review global.json changes in code review with the same seriousness as application logic.
  • Start every project with a documented global.json setup so the whole team follows the same conventions from day one.
  • Automate the boring parts of global.json with scripts or tasks; humans are bad at remembering commands.
  • Measure before and after changes to global.json so decisions are driven by data rather than vibes.
  • Prefer small, reversible changes over big-bang migrations nobody can review.

None of these are hard individually. The discipline is doing them every time, which is why automation and CI checks carry so much of the load.

Common Global.json Mistakes

The same failure patterns show up again and again. Here are the four we meet most often, including the classic: Pinning to an SDK version that contributors' platforms cannot install.

  • Copying configuration from an old project without understanding what it does today.
  • Shipping changes without a rollback plan and improvising during the incident.
  • Ignoring warnings that point at real problems because they have always been there.
  • Optimizing before measuring, then optimizing again after the metrics disagree.

Every one of these fixes is cheap when caught early and expensive when caught late. A quarterly review of global.json — twenty minutes, honestly — catches most of them before they metastasize.
