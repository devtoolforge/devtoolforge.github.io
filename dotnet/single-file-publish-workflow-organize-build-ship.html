What Is Single-file publish?

Single-file publish, in one sentence: packing the app and runtime into one executable. In practice that means the details are worth getting right once, because everything downstream inherits the decision. Once the defaults are deliberate, the rest of the workflow tends to fall into place.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around single-file publish comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Keep them separate and the rest of this guide follows naturally.

Performance Considerations

Watch the tails, not the averages. Median numbers hide the p95 and p99 latencies that users actually feel. For single-file publish workloads, repeated runs under realistic data sizes reveal the variance that a single clean run misses. Set a budget for the worst case, not the best case, and design for it.

Remove work before making work faster. The cheapest optimization for single-file publish is usually doing less: fewer allocations, fewer passes, fewer round trips. Profile to find work that can be skipped entirely under normal conditions. Only then reach for caching, and only with an explicit invalidation plan.

Troubleshooting Single-file publish

When things break, symptoms cluster into a handful of patterns. Match yours here and jump straight to the fix:

  • It works on one machine and fails on another — diff the versions and configuration first — environment drift explains most of these bugs
  • It worked yesterday and nothing was changed — check what the OS, SDK, or package manager updated overnight before blaming the code
  • It fails intermittently under load — look for shared state and timing assumptions that only break when things overlap

If none of these match, capture a full log before changing anything. For single-file publish that log almost always names the failing layer, and the fix becomes obvious instead of guessed.

Advanced Tips

Once the fundamentals are second nature, these are the practices that separate good setups from great ones:

  • Record decisions next to the code they affect, in the same pull request that introduces them.
  • Wrap external flakiness with retries and clear timeouts so failures are visible instead of mysterious.
  • Automate the audit: a scheduled check that compares expected state to real state catches drift within hours instead of months.
