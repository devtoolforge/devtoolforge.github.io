What Is Nullable reference types?

Nullable reference types, in one sentence: compile-time null safety with annotations and warnings. In practice that means the details are worth getting right once, because everything downstream inherits the decision. It is one of the few practices that pays for itself within the first week of consistent use.

The mental model is simple: one clear definition, one clear workflow, and configuration that matches reality. Most confusion around nullable reference types comes from mixing those layers — mixing definitions from different eras, or configs copied from projects with different needs. Common Nullable reference types Mistakes

The same failure patterns show up again and again. Here are the four we meet most often, including the classic: Silencing everything with null-forgiving operators instead of fixing flows.

  • Optimizing before measuring, then optimizing again after the metrics disagree.
  • Assuming the default configuration matches your project's real requirements.
  • Ignoring warnings that point at real problems because they have always been there.
  • Letting local settings drift from CI until nobody knows which one is right.

Every one of these fixes is cheap when caught early and expensive when caught late. A quarterly review of nullable reference types — twenty minutes, honestly — catches most of them before they metastasize.

Advanced Tips

Once the fundamentals are second nature, these are the practices that separate good setups from great ones:

  • Build a tiny example project that demonstrates correct usage — it doubles as a smoke test when versions change.
  • Record decisions next to the code they affect, in the same pull request that introduces them.
  • Wrap external flakiness with retries and clear timeouts so failures are visible instead of mysterious.
