ASP.NET Core Middleware Pipeline: How Requests Flow Through Your App

ASP.NET Core October 20, 2026

Every request to an ASP.NET Core application travels through a single, ordered pipeline of middleware components: the code that handles logging, exceptions, HTTPS redirection, authentication, routing, and your endpoints. Understanding this pipeline is the key mental model of the framework; most production bugs about headers, auth, or error responses trace back to middleware order.

What Is Middleware?

Middleware is a component that receives the HTTP context and either does something and calls the next component, or short-circuits and returns a response itself. Visually it is a stack of nested onions: the request passes through each layer in registration order, then the response unwinds back through them in reverse.

app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);              // continue down the pipeline
    sw.Stop();
    Console.WriteLine($"{context.Request.Path} took {sw.ElapsedMilliseconds}ms");
});

This delegate style is fine for small concerns; the conventional class pattern (with InvokeAsync and an extension method) is preferred for anything reusable.

Use, Run, and Map

Use adds middleware that can continue the pipeline (it receives a next delegate). Run terminates the pipeline, it receives no next, so it is usually the last statement or a terminal branch. Map branches the pipeline by path: everything under /jobs runs a separate branch you configure independently.

app.Map("/health", branch => branch.Run(async ctx =>
    await ctx.Response.WriteAsync("healthy")));

UseWhen branches conditionally and rejoins the main pipeline afterward, which is ideal for concerns like request logging only for specific paths.

Why Order Is Everything

Exception-handling middleware must be first so it can catch anything thrown later. HTTPS redirection before auth; static files early to short-circuit file requests cheaply; routing before endpoints; authorization immediately before endpoint mapping. Microsoft publishes a canonical ordering, and every deviation is a story: auth after endpoints means unauthenticated access, exceptions after routing means unhandled 500s.

// canonical order (simplified)
app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();  // endpoints last

The docs page 'ASP.NET Core Middleware' includes the exact diagram; print it for your team's wiki. When behavior surprises you, list your pipeline in order before reading any other code.

Writing Custom Middleware Properly

The conventional pattern: a class with a RequestDelegate constructor parameter and an InvokeAsync(HttpContext, RequestDelegate) method, plus an extension method for tidy registration. With IMiddleware, the framework resolves the component from DI per request, which enables scoped dependencies that the singleton conventional style cannot inject safely.

public class TenantMiddleware : IMiddleware
{
    public async Task InvokeAsync(HttpContext ctx, TenantService tenants)
    {
        tenants.Set(ctx.Request.Headers["X-Tenant"].ToString());
        await ctx.GetNext();
    }
}
// register: builder.Services.AddScoped<TenantMiddleware>();
//          app.UseMiddleware<TenantMiddleware>();

Whatever the style: stay fast, avoid blocking calls, remember the component runs for every matching request, and never swallow exceptions unless you are the error handler.

Debugging the Pipeline

Two techniques demystify strange behavior. First, insert lightweight Use delegates that log entry and exit with the path; the sequence printed for a single request reveals the actual flow. Second, use the developer exception page and detailed logs in Development to see which component wrote the response.

For integration tests, WebApplicationFactory lets you replace or reorder middleware, proving hypotheses quickly. When you finally fix an ordering bug, add a test that asserts the observable behavior (status code, header) so it cannot silently regress.

Conclusion

The middleware pipeline is ASP.NET Core's whole architecture in one picture: ordered components wrapping every request. Learn Use/Run/Map, respect the canonical order, write custom middleware in the conventional or IMiddleware style, and you can explain, debug, and extend any ASP.NET Core app from the inside out.

Frequently Asked Questions

What is the difference between Use and Run?

Use registers middleware that receives a next delegate and can continue the pipeline; Run registers terminal middleware with no next, ending the request at that point.

Why does middleware order matter so much?

Each component sees the request only if earlier ones pass it on, and responses unwind in reverse. Wrong order breaks exception handling, authentication, and static file performance in subtle ways.

Can middleware depend on scoped services?

Conventional middleware is constructed once, so only singletons are safe to inject via constructor. Use IMiddleware (resolved per request from DI) or invoke scoped services inside InvokeAsync parameters.

How do I branch the pipeline for a path?

Map creates a branch for a path prefix with its own middleware configuration; UseWhen branches conditionally and rejoins the main pipeline afterward.

Where should UseAuthentication go?

After UseRouting and before UseAuthorization and endpoint mapping, so that authentication information exists when authorization decisions run.
